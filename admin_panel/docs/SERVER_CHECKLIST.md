# چک‌لیست سرور (نگهداری و جابجایی)

> هر تغییری در کد که به تنظیمات روی سرور نیاز دارد (متغیر محیطی جدید، پوشه‌ی جدید، پورت، کرون، nginx، سرویس خارجی ...) باید همین‌جا ثبت شود. این فایل منبع حقیقت «چیزهایی که در git نیستند ولی برنامه به آن‌ها نیاز دارد» است.

## ۱. موجودی: چه چیزهایی فقط روی سرور هستند
| مورد | سرور | محل | در بکاپ؟ |
|---|---|---|---|
| تنظیمات واقعی برنامه (JWT، DB، ...) | بک‌اند | `~/nopa.env` (hook آن را به `~/nopa/.env` کپی می‌کند) | بله (داخل آرشیو رمزشده) |
| فایل‌های چت | بک‌اند | `CHAT_FILES_DIR` (پیشنهادی `~/nopa-data/chat-files`) | بله |
| آپلودهای عمومی | بک‌اند | `~/nopa/uploads` | بله |
| فایل‌های نصب اپ (APK به تفکیک معماری) | بک‌اند | `~/nopa/uploads/apk` | **نه، عمداً** (روی سیستم انتشار در `app/build/releases/` می‌ماند؛ از پنل دوباره بارگذاری می‌شود) |
| تنظیم بکاپ | بک‌اند | `~/backup.env`, `~/.backup-pass` | **نه؛ دستی نگه دارید** |
| زمان‌بندی بکاپ | بک‌اند | `crontab -l` | نه |
| hook دیپلوی | بک‌اند | `~/repos/nopa.git/hooks/post-receive` | از git (`deploy/post-receive`) |
| تنظیم nginx (از جمله `/socket.io/`) | بک‌اند | `/etc/nginx/...` | نه (نمونه: `deploy/nginx-chat.conf`) |
| PM2 و راه‌اندازی بعد از ریبوت | بک‌اند | `pm2 startup` + `pm2 save` | نه |
| دیتابیس و تنظیم Supabase | دیتابیس | `docker compose` + `.env` سوپابیس | دیتابیس بله؛ `.env` سوپابیس **نه** |
| فایروال | هر دو | `ufw status` | نه |
| DNS و CDN آروان (WebSocket روشن) | پنل ابری | رکوردهای دامنه | نه |
| رمزنگاری دیسک | هر دو | LUKS یا پنل ابری | — |
| پسورد رمزگشایی بکاپ | password manager | خارج از سرور | — |

## ۲. چک‌لیست جابجایی یا ساخت مجدد سرور بک‌اند
- [ ] سرور جدید: اوبونتو، Node.js، PM2 (`pm2 startup` + `pm2 save`)، nginx، `postgresql-client`، `gnupg`، `rsync`، ufw.
- [ ] ریبوت‌پروف: بعد از ریبوت، PM2 و nginx خودشان بالا بیایند.
- [ ] `~/repos/nopa.git` را بسازید و `deploy/post-receive` را کپی و `chmod +x` کنید؛ ریموت git را عوض کنید.
- [ ] `~/nopa.env` را از سرور قبلی یا از آرشیو بکاپ (`app.env`) برگردانید. اگر IP یا آدرس DB عوض شده `DATABASE_URL` و `DIRECT_URL` را درست کنید.
- [ ] `JWT_SECRET` همان قبلی باشد، وگرنه همه‌ی توکن‌ها و لینک‌های فایل بی‌اعتبار می‌شوند.
- [ ] `CHAT_FILES_DIR` را بسازید (`chmod 700`) و فایل‌های چت و `uploads/` را از آخرین بکاپ برگردانید.
- [ ] IP جدید بک‌اند را روی **سرور دیتابیس** باز کنید (`ufw allow from <IP> to any port 5432` و `6543`) و IP قدیمی را ببندید.
- [ ] nginx: بلوک `deploy/nginx-chat.conf` (`/socket.io/`) را اضافه کنید؛ `nginx -t && systemctl reload nginx`؛ تست WebSocket (دستور داخل خود فایل).
- [ ] اگر آروان جلوی سرور است: IP مبدأ را در پنل آروان عوض کنید و WebSocket روشن باشد. SSL را دوباره بگیرید یا کپی کنید.
- [ ] DNS: رکورد `nopa-app.ir` را به IP جدید ببرید (TTL را قبلش کم کنید).
- [ ] `git push` برای دیپلوی و بررسی: `pm2 status`، `curl https://nopa-app.ir/api/v1/...`، ورود به اپ، ارسال یک پیام و یک فایل در چت.
- [ ] بکاپ را دوباره نصب کنید: `~/backup.env`، `~/.backup-pass` (همان پسورد قبلی)، `crontab`، کلید SSH به ماشین مقصد؛ یک اجرای دستی `backup.sh` و دیدن فایل روی مقصد.
- [ ] روی سرور قدیمی: بعد از اطمینان، داده‌ها را **پاک امن** کنید (چت خصوصی در آن است) و دیسک را حذف کنید.
- [ ] اپ فلاتر از `api_constants.dart` به دامنه وصل می‌شود؛ اگر دامنه عوض شد باید نسخه‌ی جدید اپ منتشر شود.

## ۳. چک‌لیست جابجایی سرور دیتابیس (Supabase)
- [ ] روی سرور جدید طبق `SUPABASE_SELF_HOST.md` نصب کنید؛ **همان** `POSTGRES_PASSWORD`، `JWT_SECRET` و `POOLER_TENANT_ID`.
- [ ] آخرین dump را بازیابی کنید (بخش «بازیابی» در `BACKUP_AND_PRIVACY.md`)، سپس `npx prisma migrate deploy`.
- [ ] رکورد `db.nopa-app.ir` در حالت DNS only به IP جدید؛ ufw فقط برای IP بک‌اند.
- [ ] `DATABASE_URL`/`DIRECT_URL` بک‌اند و `backup.env` را اگر آدرس عوض شده اصلاح کنید و `pm2 restart nopa --update-env`.
- [ ] نسخه‌ی `pg_dump` سرور بک‌اند هنوز >= نسخه‌ی PostgreSQL جدید باشد.
- [ ] `.env` سوپابیس را در بکاپ جدا و امن نگه دارید.

## ۴. کارهای دوره‌ای
| دوره | کار |
|---|---|
| هفتگی | `tail ~/backups/backup.log`؛ وجود فایل دیشب روی بک‌اند و ماشین مقصد |
| هفتگی (موقت، تا وقتی سرور پشتیبان نیست) | آخرین فایل `~/backups/nopa_*.tar.gpg` و `.sha256` را با `scp` به سیستم شخصی بکشید و آن‌جا نگه دارید؛ `OFFSITE_TARGET` را بعد از تهیه‌ی مقصد در `~/backup.env` فعال کنید |
| ماهانه | `df -h` هر دو سرور؛ `apt upgrade`؛ `pm2 status`؛ بررسی انقضای SSL؛ اندازهٔ جدول `UserActivityLog` (لاگ فعالیت اپ) |
| هر ۳ تا ۶ ماه | بازیابی تمرینی کامل بکاپ روی سرور تست |
| سالانه | چرخاندن رمزها (پسورد DB، JWT، پسورد بکاپ؛ پسورد قدیمی را برای بکاپ‌های قدیمی نگه دارید) |

## ۵. هنگام تغییر کد
اگر تغییر شما یکی از این‌ها را شامل می‌شود، قبل از پایان کار، این فایل (جدول بخش ۱ و چک‌لیست‌ها) را به‌روز کنید:
- متغیر محیطی جدید در `.env` (در `nopa.env` سرور هم اضافه شود)
- پوشه یا فایل ماندگار جدید روی دیسک (باید وارد `backup.sh` شود)
- پورت، دامنه، مسیر nginx یا نیاز به WebSocket جدید
- سرویس خارجی یا کرون جدید
- تغییر schema پریسما (migration)، که hook خودش `migrate deploy` می‌زند ولی باید قبلش بکاپ گرفته شود

### یادداشت: واکنش‌های جدید پیام‌های چت
- `REACTION_TYPES` در `src/modules/chat/service.ts` به `like, dislike, idea, flower, thanks` (و کلیدهای قدیمی برای واکنش‌های ثبت‌شده) گسترش یافت. بدون استقرار مجدد بک‌اند، اپ جدید با خطای «واکنش نامعتبر است» روبه‌رو می‌شود. نیازی به migration نیست.

### یادداشت: بررسی نسخه‌ی جدید اپ
- مسیر عمومی `GET /api/v1/app/version` (در `src/app.ts`) اضافه شد؛ بک‌اند باید دوباره مستقر شود.
- **به‌روزرسانی (۱۴۰۵/۰۸/۱۴):** آخرین نسخه، لینک دانلود و تغییرات حالا از پنل تنظیم می‌شوند: تب «امنیت و دسترسی» ← کاشی «نسخه اپلیکیشن» (فقط سوپر ادمین؛ مسیرهای `GET/PUT /api/v1/admin/app-release`). مقدار در جدول `SystemSetting` با کلید `APP_LATEST_RELEASE` ذخیره می‌شود، پس در بکاپ دیتابیس هست و نیازی به migration، `pm2 restart` یا متغیر جدید نیست. فقط بک‌اند باید دوباره مستقر شود.
- متغیرهای قدیمی `APP_LATEST_VERSION`، `APP_DOWNLOAD_URL` و `APP_RELEASE_NOTES` در `~/nopa.env` اختیاری‌اند و فقط تا وقتی که یک بار از پنل ذخیره نشده استفاده می‌شوند؛ بعد از اولین ذخیره از پنل می‌توان آن‌ها را پاک کرد.
- اگر نسخه خالی باشد (دکمه «توقف اعلان» در پنل)، اپ پیام «آخرین نسخه را دارید» نشان می‌دهد.
- **به‌روزرسانی (۱۴۰۵/۰۸/۱۵): فایل به تفکیک معماری.** `scripts/release_app.js` حالا سه APK سبک می‌سازد (`arm64-v8a`، `armeabi-v7a`، `x86_64`). در فرم پنل هر معماری ردیف خودش را دارد و فایل همان‌جا بارگذاری می‌شود (`POST /api/v1/admin/app-release/apk`، فقط سوپر ادمین، تا ۱۵۰ مگابایت) و در `~/nopa/uploads/apk` ذخیره می‌شود؛ مسیر دانلود `/uploads/apk/...`. فایل‌هایی که نسخه‌ی فعلی به آن‌ها لینک ندارد و بیش از ۳۰ روز از عمرشان گذشته، با بارگذاری بعدی خودکار پاک می‌شوند. `GET /api/v1/app/version` حالا `downloads` (لینک هر معماری) و `universalUrl` را هم برمی‌گرداند؛ اپ‌های قدیمی همان `downloadUrl` را می‌خوانند که در نبود نسخه‌ی کامل، لینک arm64 است.
  - [ ] بک‌اند را مستقر کنید و `pm2 restart` بزنید (migration و متغیر جدید ندارد).
  - [ ] **nginx:** برای مسیر بارگذاری سقف بدنه را بالا ببرید، وگرنه بارگذاری APK با خطای ۴۱۳ رد می‌شود. داخل `server { ... }` دامنه، **قبل از** `location /` عمومی:
    ```nginx
    location = /api/v1/admin/app-release/apk {
        client_max_body_size 160m;
        proxy_request_buffering off;
        proxy_read_timeout 300s;
        proxy_pass http://127.0.0.1:5000;   # همان PORT فایل .env و مقصد location / فعلی
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
    ```
    سپس `nginx -t && systemctl reload nginx`. اگر آروان جلوی سرور است، سقف حجم درخواست آن هم باید حداقل ۱۶۰ مگابایت باشد (یا فایل را با لینک خارجی بگذارید).
  - [ ] یک بار در پنل یک APK بارگذاری کنید و لینک ساخته‌شده را در مرورگر باز کنید؛ باید دانلود شود (نه نمایش).
  - [ ] پوشه‌ی `uploads/apk` در بکاپ نیست (`deploy/backup.sh` با `--exclude=./apk`)؛ بکاپ‌های قبلی تغییری نمی‌کنند.

### یادداشت: محدودیت درخواست، لینک فایل‌های چت و اتصال
- سقف `apiLimiter` از ۱۰۰۰ به ۶۰۰۰ درخواست در ۱۵ دقیقه برای هر کاربر رفت (`src/middleware/rateLimit.ts`)؛ مسیر `/api/v1/chat/files/` از شمارش معاف شد. سقف قبلی با همگام‌سازی هر ۳ ثانیه‌ی اپ پر می‌شد و بعد از آن واکنش، ارسال پیام و اتصال با خطای ۴۲۹ شکست می‌خوردند.
- مسیر جدید `GET /api/v1/chat/attachments/:id/link` (لینک تازه برای فایل‌های ذخیره‌شده) اضافه شد؛ بدون استقرار مجدد بک‌اند، پخش صدا برای پیام‌های قدیمی همان خطا را می‌دهد.
- بعد از استقرار `pm2 restart` بزنید. نیازی به migration نیست. در صورت استفاده از nginx/آروان مطمئن شوید WebSocket روی `/socket.io/` روشن است (اگر خاموش باشد اپ «درحال اتصال...» می‌ماند و فقط با polling کار می‌کند).

### یادداشت: سقف ۳۰ مگابایت برای فایل‌های چت
- سقف آپلود چت (`MAX_FILE_BYTES` در `src/modules/chat/controller.ts`) از ۲۰ به ۳۰ مگابایت رفت. اپ فایل‌های بزرگ‌تر را اصلاً نمی‌فرستد و پیام خطا نشان می‌دهد.
- در nginx (و آروان، در صورت استفاده) مقدار `client_max_body_size` باید حداقل `32m` باشد، وگرنه فایل‌های بین ۲۰ تا ۳۰ مگابایت با خطای ۴۱۳ رد می‌شوند. بعد از تغییر: `nginx -t && systemctl reload nginx`، سپس `pm2 restart`.

### یادداشت: ستاره‌ی «برتر» برای راهبران
- نوع واکنش جدید `star` (فقط برای کسانی که `canModerate` دارند) به `REACTION_TYPES` اضافه شد و جستجوی `#برتر` پیام‌های ستاره‌دار را برمی‌گرداند. جدول و ستون جدید ندارد (از `ChatReaction` موجود استفاده می‌کند)، پس **migration لازم نیست**؛ فقط بک‌اند را مستقر و `pm2 restart` کنید. تا آن موقع زدن ستاره در اپ خطا می‌دهد.

### یادداشت: میدان آثار برای راهبران و «گروه رسانه»
- قوانین `src/modules/chat/access.ts` عوض شد: راهبران در «میدان آثار» پیام می‌دهند و پاسخ می‌دهند؛ دانش‌آموزان همچنان فقط در گروه چالش‌های کاروان خودشان گفتگو می‌کنند.
- فضای عمومی جدید `mediaqa` («گروه رسانه») برای همه‌ی کاربران: خودش هنگام اولین باز شدن چت ساخته می‌شود. نیازی به migration نیست؛ فقط بک‌اند باید دوباره مستقر شود (`pm2 restart`).

### یادداشت: نمودار زمان حضور اعضا در اپ و مشارکت در چالش‌ها (صفحهٔ «اعضا و کاروان» راهبر)
- جدول جدید `UserUsageDay` (migration با نام `20261061_user_usage_day`): هر کاربر در هر روز (به وقت تهران) ثانیه‌هایی که اپ باز و در پیش‌زمینه بوده. اپ هر حدود یک دقیقه `POST /api/v1/usage/ping` می‌زند؛ هر درخواست حداکثر ۳۰۰ ثانیه می‌افزاید.
- قبل از استقرار از دیتابیس بکاپ بگیرید؛ hook استقرار خودش `prisma migrate deploy` را می‌زند. بعد `pm2 restart` بزنید. بدون استقرار بک‌اند، اپ جدید فقط نمودار زمان را خالی نشان می‌دهد (خطا نمی‌دهد).
- پاسخ `GET /api/v1/mentor/caravan-progress` دو فیلد تازه برای هر عضو دارد: `challengesByStation` و `usageDays` (۳۰ روز اخیر). فقط زمان حضور ثبت می‌شود، نه صفحه‌ها یا محتوا؛ داده با حذف کاربر پاک می‌شود (`onDelete: Cascade`).
- ورودی جدید در `.env` و فولدر ماندگار جدید لازم نیست.

### یادداشت: چالش‌های میان‌گروهی در «میدان آثار» و گروه چالش‌های کاروان
- کارت چالش در «گروه چالش‌ها»ی هر کاروان حالا با هویت راهبر همان کاروان منتشر می‌شود (`src/modules/chat/topics.ts`)؛ چالش میان‌گروهی هم‌زمان در «میدان آثار» می‌آید.
- فایلی که راهبر زیر چالش در «میدان آثار» می‌فرستد «اثر کاروان» حساب می‌شود و برای رتبه‌بندی مدیر ثبت می‌شود (`recordArenaSubmission`)؛ تا پایان مهلت از کاروان‌های رقیب پنهان است (بخش «فاز ۱» پایین همین فایل). بعد از تأیید یا اصلاح رتبه‌بندی، نشان مقام روی همان پیام‌ها نشان داده می‌شود (`applyRankBadges`).
- نیازی به migration، متغیر محیطی یا فولدر جدید نیست؛ فقط بک‌اند باید دوباره مستقر شود (`pm2 restart`). بدون آن، اپ جدید فقط کارت‌های قدیمی (بدون نام راهبر و نشان مقام) را نشان می‌دهد و خطا نمی‌دهد.
- کارت‌های چالشی که قبلاً منتشر شده‌اند، پس از ویرایش آن چالش (که `syncChallengeCards` را اجرا می‌کند) به هویت راهبر به‌روز می‌شوند.

### یادداشت: ایمیج Docker و محیط تست بار (`loadtest/`)
- `Dockerfile` چندمرحله‌ای شد: ایمیج نهایی (`runner`) فقط وابستگی‌های production دارد، با کاربر غیر root اجرا می‌شود و دیگر `uploads/` را داخل ایمیج کپی نمی‌کند (`uploads` و `CHAT_FILES_DIR` باید volume باشند).
- **مهم:** ایمیج دیگر خودش `prisma migrate deploy` نمی‌زند. اگر روزی بک‌اند با Docker اجرا شد، قبل از آن target `migrator` را اجرا کنید (`docker build --target migrator` و اجرای آن با `DATABASE_URL`/`DIRECT_URL`). روی سرور فعلی (PM2 + hook) هیچ تغییری لازم نیست.
- PDF (html-pdf-node) در ایمیج Docker کار نمی‌کند، چون Chrome ندارد.
- `loadtest/` فقط برای اجرا روی سیستم توسعه یا یک سرور تست است (Postgres و PgBouncer و Redis جدا). هرگز آن را روی سرور production یا با `DATABASE_URL` واقعی اجرا نکنید؛ اسکریپت‌ها هم خودشان روی هر آدرسی غیر از sandbox متوقف می‌شوند. راهنما: `loadtest/README.md`.
